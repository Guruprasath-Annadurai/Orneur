# GENESIS V2 — Threat & Compromise Matrix (Adversarial Self-Review)

Status: **DESIGN ONLY.** This document attacks the architecture proposed in the rest of this package, as the "GOD-MODE adversarial review" the task requested, and records what was patched as a result.

## Assumptions (per the task's own zero-trust framing)

Generator may be compromised. Verifier may be compromised. CI may be compromised. Cloud account credentials may leak. A developer workstation may be compromised. Network traffic may be observed. Object storage may be copied. Repository write access may be abused. Individual runtime processes may be hostile.

## Compromise-containment matrix

| Compromised component | What attacker gets | What they still cannot get | Detection | Recovery |
|---|---|---|---|---|
| **Generator (Forge)** | Generator identity's write credential; the generator code it was running; the X25519 **public** key and corpus secret it held | X25519 private key (never present); ability to decrypt any ciphertext, past or future; owner signing key; ability to forge a valid CGA or a valid owner-signed receipt (requires the owner's private key, never on Forge) | Unexpected process identity on Forge host; repeated/failed writes; Evidence Ledger entries with no corresponding owner-signed receipt | Revoke generator identity, rotate the X25519 keypair for future corpora (compromise of the public key alone is not itself damaging, but a compromised Forge could have substituted forged ciphertext — see the receiving-boundary authentication chain, which specifically defeats this), rebuild Forge from pinned image |
| **Verifier (Witness)** | Verifier identity; **the X25519 private key** — this is the highest-severity single-component compromise in the whole system | Owner signing key; generator's write credential; ability to forge an owner signature on a CGA/receipt/manifest | Unexpected decrypt attempts outside the ledger-gated path; ledger replay attempts; anomalous read volume | Treat EVERY corpus this Witness instance could have decrypted as confidentiality-lost; rotate keys for all future corpora; revoke verifier identity; rebuild from pinned image; see Incident Runbook's Witness-compromise section |
| **Owner workstation (Crown Plane)** | Potentially the owner's private signing key, if the workstation itself (not just the Keychain/hardware-token boundary) is compromised deeply enough | — nothing, if a hardware token (Tier 1+) was used correctly, since the private key material never actually resides on the workstation, only a challenge-response capability does. Tier 0 Keychain-only custody is weaker here — this is exactly why Tier 1's hardware token is the recommended graduation, not merely a nice-to-have | Unexpected signing operations in the authority registry's own history (every signature is itself public, auditable evidence); owner's own awareness of unexpected prompts from a hardware token | Revoke authority key immediately; treat every signature from the compromise window as void; re-key via a fresh ceremony on a clean workstation |
| **Public GitHub repo** | Full read access to all registries, code, evidence snapshots, CI workflow definitions — all of which are already intentionally public | Any secret (none are stored there by design); any plaintext corpus content; write access (requires separate repo-write credentials, themselves never co-located with vault/signing credentials) | GitHub's own audit log for any write; unusual force-pushes or history rewrites on protected branches | Standard GitHub security response (rotate repo-write credentials, review branch protection); does not by itself compromise any Genesis V2 secret because none exist there |
| **CI (GitHub Actions)** | Whatever the CI job's own scoped token can do — today, that's running tests and reading public repo content; after this phase, also running the synthetic acceptance suite, still against no real secrets | Any Genesis V2 secret (none are ever passed to the 6 mandatory jobs or the new synthetic-acceptance job); real vault access; any signing capability | GitHub Actions' own run logs; unexpected workflow-file changes (code review on every PR already covers this) | Revoke the specific compromised token/credential; this incident class should never reach Genesis V2 material in the first place given the network-policy rule that CI never touches real key material |
| **Vault storage account (cloud, Tier 1+)** | All ciphertext for every corpus stored there | Any plaintext (ciphertext is useless without the separately-custodied private key); any secret; any signing capability | Cloud-native access log anomalies; unexpected egress volume; object-lock/versioning tamper attempts | Revoke the compromised credential; rotate vault storage access keys; because ciphertext alone is harmless, this incident does NOT by itself require regenerating any corpus — only Witness-key compromise does |
| **Backup account (Reliquary)** | All backed-up ciphertext | Same as Vault storage — ciphertext alone is harmless without the private key, which is never backed up here by design | Same pattern as Vault storage | Revoke credential, rotate backup access, confirm no private key was ever present (design-time guarantee, should be a quick confirmation) |
| **Evidence store** | Digests, signatures, hashes, ledger records, identity metadata — all designed to be safe to disclose (none of it is itself a secret) | Plaintext; any secret; any key | Hash-chain tamper-evidence already built into `AccessLedger`; unexpected gaps/edits in the append-only trail | Restore from the most recent trusted (e.g. git-committed, or Tier 1+ immutable-store) copy; investigate the gap as a potential tamper attempt, not just data loss |
| **DNS / edge (not applicable to Genesis V2 at any tier in this design — no Genesis V2 component has a public endpoint)** | n/a | n/a | n/a | n/a — explicitly out of scope because the architecture gives this attacker nothing to target |
| **Cloud control plane (Tier 1+, e.g. the cloud account's own root/org-admin)** | Everything in that specific account — this is why multi-account separation matters: a compromised control-plane identity in the Vault account should not also control the Witness account or the owner's signing material | Owner signing key (never cloud-resident at any tier); the *other* accounts, if account separation was genuinely maintained (not just separate IAM roles in one account) | Cloud provider's own control-plane audit log (e.g. root-login alerts, org-policy changes) | Full account-level incident response per the cloud provider's own break-glass procedure; this is the scenario multi-account separation exists specifically to contain |

## Adversarial role-play — what was checked, and what was patched

- **As a malicious generator**: can it make SCREEN/HOLDOUT leak? No — it never holds decrypt capability, structurally. Can it get false generation accepted? It can write *forged* ciphertext + a self-consistent-looking manifest claiming arbitrary content, but cannot produce a valid owner signature over that manifest, and cannot produce a valid `generation_receipt` without the owner's signature either (the generator never holds the owner's key by design) — this exact attack was the subject of the receiving-boundary-integration and generation-provenance-closure phases' adversarial test suites, already in the codebase, and is why this architecture document explicitly does not need to invent new countermeasures here: the *code* already closes this path; infrastructure's job is to not accidentally hand the generator something (like the owner key) that would reopen it.
- **As a malicious verifier**: can it see more than it should? It can see real plaintext for the specific corpus it's authorized to verify — that is its job, and the lifecycle controls (purpose separation, ledger write-once holdout state) bound how much and for how long. Can it forge acceptance of an unauthorized corpus? No — it only decrypts what the receiving-boundary chain has already authenticated; it cannot bypass that chain from its own side.
- **As a compromised GitHub Actions runner**: can it exfiltrate a secret? Only if a secret were ever passed to it — this design's explicit rule (network policy, IAM matrix) is that it never is for the 6 mandatory jobs or the new synthetic-acceptance job. **Patch applied during this review**: confirmed the proposed synthetic acceptance test (`tests/test_genesis_v2_deployment_acceptance_synthetic.py`) must never read any real environment variable that could coincidentally hold production secret material — it uses only locally-generated ephemeral keys, exactly like every existing test in the suite, and this is called out explicitly in that file's own module docstring.
- **As a rogue developer with repo-write access**: can they authorize generation? No — repo-write lets them propose a change (e.g. edit a registry file), but every registry entry that matters is either structurally non-authorizing on its own (registration ≠ authorization, already true in code) or requires a real Ed25519 signature from a key they don't have. **Patch applied**: the IAM matrix explicitly denies Deployment Automation (which could be driven by a rogue developer's PR, if merged) any "Owner Sign" capability — this was verified as already true of the existing code design and is restated here as an infrastructure-identity rule, not newly invented.
- **As an attacker holding only the vault ciphertext**: gets nothing (confidentiality holds by the existing crypto design) — already proven adversarially in the receiving-boundary-integration phase's test suite (forged-substitution tests).
- **As an attacker holding only the X25519 public key**: can encrypt arbitrary content but cannot forge a trusted manifest/receipt without the owner's signature — already proven in the deployment-decision-accuracy-closure phase's adversarial tests.
- **As an attacker with verifier host access** (not just the key, the whole host): sees plaintext for whatever that Witness instance can legitimately decrypt — this is the single scenario where real harm (plaintext confidentiality loss) occurs purely from infrastructure compromise rather than requiring the owner's key too, which is exactly why this document treats Witness compromise as the highest-severity infrastructure incident class and why Domain 2's design insists on genuine process isolation, proven (not merely documented) before go-live.
- **As an attacker with backup access**: ciphertext only, harmless, confirmed above.

No weakness was found in this review that required changing the already-accepted software controls (per the task's own instruction not to redesign them). The infrastructure-level patches applied during this review were: (1) explicit confirmation that CI never receives real secret material, including for the new synthetic acceptance suite; (2) explicit multi-account separation requirement at Tier 1+ specifically to contain a cloud-control-plane compromise; (3) explicit flagging of Witness compromise, not Forge compromise, as the single highest-severity infrastructure incident, driving the "real process isolation is mandatory, not optional" rule in the Trust Domain Model and the Deployment Acceptance criteria.

## Canonical owner-key policy

**Canonical owner-key policy (audit closure): the owner Ed25519 signing private key MUST remain owner-controlled and non-cloud-resident at every tier. A local hardware token/HSM physically controlled by the owner is permitted; a cloud KMS/HSM holding the owner signing private key is not compatible with this architecture.**
