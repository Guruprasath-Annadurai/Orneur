# Genesis V2 — Tier0-S: Sequential Sovereign Isolation (single physical machine, REDUCED ASSURANCE)

**Decision gate: `TIER0_S_REDUCED_ASSURANCE_ONLY`.** Tier0-A remains `TIER0_A_BLOCKED_SECOND_MACHINE_REQUIRED` (historical conclusion, unchanged). Tier0-S is a separate fallback and is **never equivalent to Tier0-A**. Design + synthetic validation only: no real secret, no corpus, no purchase, no disk/boot/security change, no reboot, no model, no GPU, no cloud, no spend.

Assurance order: **Tier0-B** (concurrent single-host containers) **<** **Tier0-S** (sequential isolated environments) **<** **Tier0-A** (two physically independent machines).

## 0. Limitations — read first (not softened)
Tier0-S may protect against: accidental cross-role leakage; a compromised Forge process; a compromised Witness process; a shared container daemon between concurrently active roles; simultaneous runtime cross-control; straightforward role-secret mixing.

Tier0-S does **NOT** protect against, and must never claim to:
- compromise of the physical Mac itself;
- firmware / boot-chain compromise;
- a **malicious owner or root administrator** — the owner/root on one physical Mac can ultimately influence both environments over time (edit the gate, the receipts, the images, or the machine). Tier0-S has **no adversarial-owner isolation and no independent physical custody**;
- hardware-level compromise;
- persistence deliberately planted across both boot environments;
- a privileged attacker with access to both encrypted environments over time.
Real-secret activation under Tier0-S requires **explicit owner risk acceptance** (Decision 9, open).

The software phase gate (§9) is one-shot, advisory and bypassable by anyone who can write the files it reads or alter the machine; it is **not** a hardware or adversary-resistant boundary and it is not what provides cold-boot or detachment separation.

## 1. Definition and lifecycle (with PHYSICAL DETACHMENT)
Forge and Witness are **never simultaneously active**, and **the other role's storage is never simultaneously available**. Each role runs in its own separately encrypted environment, entered only by a **full shutdown and cold boot** (not container stop/start, not sleep, not user switch). Only ciphertext crosses the boundary, through the audited transfer-bundle tooling (`scripts/genesis_v2_tier0a_transfer_bundle.py`). The owner signing key is in none of the environments.

**Cold boot and PHYSICAL DETACHMENT are owner-controlled physical procedures.** They are the actual separation controls. No software on the machine enforces them against the machine's owner, and the software gate (§9) earns NO acceptance credit for them.

Exact lifecycle for S1 / S1+ (wherever the topology permits physical detachment; the floor design's internal drive cannot be detached, which is one reason it is weaker):
1. Crown/Owner signs the authorization on the owner plane (off both machines' role storage).
2. Forge storage attached/active; **Witness storage physically absent** (disconnected, not merely unmounted or locked). The transfer medium is blank/approved.
3. Cold boot the Forge environment. Run the phase gate (`check`, then `begin`). Forge phase: generate; plaintext only in RAM.
4. Seal the ciphertext bundle onto the transfer medium (`seal`). Forge shutdown (full power-off).
5. After shutdown, remove Forge role storage where applicable (**physically disconnect it**). Attach **ONLY the approved transfer medium and the Witness storage**; the Forge storage stays absent.
6. Cold boot the Witness environment. Run the phase gate. `validate_and_stage` the bundle (read-once validated copy), then `cryptographic_verify` with the Witness private key.
7. Witness phase: decrypt/verify, write evidence. Full shutdown.
8. Erase / re-encrypt the transfer medium per the owner procedure.
**No simultaneous mounting of Forge and Witness secret-bearing storage, at any step.** Keeping networking disabled for the **whole** phase is also an owner procedure (the gate checks it once, at phase start only).

## 4. Recommended model
**S1+**: two dedicated minimal environments on separate encrypted external drives, a third ciphertext-only transfer medium, owner signing key elsewhere. **Floor (explicitly weaker)**: S1 with the internal macOS as Forge, permitted only after the Forge-phase channels in §6 are mitigated and `genesis_v2_tier0s_phase_gate.py` passes. **Not acceptable**: the current daily-driver environment as-is (the v4 gate, run read-only against it with a valid initialized throwaway interlock directory and the full repository as code root, passes 7 of 16 checks, FAILS 6 and FAILS CLOSED on 3: container runtime, sockets and install directories present; network addresses and default routes present; AI-agent processes running and agent transcript/index stores holding data; synchronized locations holding data; the repository tree containing symlink/special objects so it cannot be matched to the role-code manifest; and the socket table unreadable under this Python on this host).

## 5. Storage separation
- **Forge environment** (own encryption, own passphrase): corpus-generation secret, X25519 public key, Generator identity; plaintext only in RAM / an ephemeral RAM disk during generation, never written to persistent storage.
- **Witness environment** (own encryption, own passphrase, a *different* passphrase held separately): X25519 private key, Verifier identity, encrypted Vault, evidence.
- **Transfer medium**: ciphertext + `MANIFEST.json` only (validator-enforced); erased/re-encrypted after use.
- **Owner signing key**: separate from all three (owner-controlled hardware token / Keychain / local HSM; never cloud).
Neither environment may carry the other's passphrase or recovery key. No real secret is created in this phase.

## 6. Residual-state / persistence analysis
Classification is for the **daily-driver internal environment on this host** unless noted. The **Enforcement** column says what actually backs each control, using a closed vocabulary: `GATE_CHECKED` (the software phase gate inspects it, within the stated limits) · `OWNER_PROCEDURE` (a control the owner must perform; nothing verifies it) · `DESIGN_ASSUMPTION` (relied on, observed or inferred, not verified at phase time) · `NOT_CHECKED` (the gate does not look at it) · `NOT_PROVEN` (the property is not established). **A row may claim `GATE_CHECKED` only for a channel the gate genuinely inspects; the test suite enforces this.**

| Channel | Class | Enforcement | Basis |
|---|---|---|---|
| Shared internal filesystem | `MITIGATABLE` | `OWNER_PROCEDURE` `NOT_PROVEN` | Internal volumes are FileVault-locked while another OS runs; the control is never entering the other role's credential in a role environment. Nothing verifies it. |
| Swap | `CONTROLLED` | `DESIGN_ASSUMPTION` `NOT_CHECKED` | Observed encrypted on this host at discovery; per-boot key discarded at shutdown. The gate does not read swap state. |

**Verdict on the persistence gate:** two secret-bearing channels (cloud sync, agent stores) are `UNCONTROLLED` on the daily-driver, so the daily-driver is **not** a valid Tier0-S Forge environment. A dedicated environment (S1+) can bring them under control; that has not been provisioned or proven.

**What survives a reboot and could be a cross-role channel:** internal-disk contents (locked but present), the transfer medium (ciphertext only), NVRAM/firmware state, logs and reports on persistent volumes, and anything the owner carries in their head or password manager (passphrases, recovery keys). Each is addressed above or listed as unproven.

## 7. Docker / runtime boundary
No container daemon may be alive during a role phase (gate check `container_runtime_absent`); roles run as plain, non-persistent processes. Tier0-B container isolation does **not** transfer to Tier0-S as proof; Tier0-S relies on the owner-controlled boot and detachment procedure, not on a daemon boundary.

## 8. Transfer boundary
Forge → `seal` → transfer medium → **shutdown / cold boot** (storage swapped per §1) → Witness runs `validate_and_stage` before any import, then `cryptographic_verify`. Allowed: `SCREEN.enc`, `QUALIFICATION_HOLDOUT.enc`, `SEAL.enc`, `MANIFEST.json`. Forbidden: plaintext, corpus-generation secret, X25519 private key, owner key, Witness credentials.

**Claim levels (do not conflate):**
- `EXPECTED_ENCRYPTED_ARTIFACT_FORMAT_VALIDATED` — keyless `validate` / `seal` / `validate_and_stage`: expected files only, encrypted-artifact magic, allowlisted well-formed header matching the path, plausible size, strict manifest (duplicate keys rejected), no symlinks, no hardlinks, digests match. **This is a shape check; a file with a valid header followed by plaintext passes it (tested).** It is not proof of encryption and entropy is not used as proof.
- `CRYPTOGRAPHICALLY_VERIFIED` — `cryptographic_verify`, Witness side only, with the vault private key and the expected corpus digest: every split and the SEAL authenticate under AES-256-GCM (a plaintext payload fails the tag check) and digests match. The only keyed, real proof; library function only.
Authenticity of the generator is a separate matter (signed generation receipt). The staged copy narrows the validate→import race (read-once, same bytes written read-only); a writer with control of the staging directory (same host user/root) can still alter it. Every member is `lstat`-ed before any open: a FIFO, socket, device, directory, symlink or hardlink is rejected without being opened (so a special file cannot make validation hang), and the open uses `O_NOFOLLOW|O_NONBLOCK` with the descriptor re-checked against the `lstat`. Operational note: `._*` and `.DS_Store` entries on foreign filesystems are rejected (fail closed).

## 9. Software phase gate (v4) — honest scope
`scripts/genesis_v2_tier0s_phase_gate.py` is a **one-shot, advisory, software-level, fail-closed pre-flight** run at the start of a role phase. It passes only if **every** check is `PASS`. The governing rule is *unknown state is unsafe state*: any missing input, unavailable/unsupported/permission-denied host query, telemetry that does not match the strict structure the gate expects, or filesystem object it cannot fully and safely enumerate is `FAIL_CLOSED`. The parsers bound what is accepted as well-formed; they do **not** prove that well-formed telemetry is complete or true (a source that removes whole, well-formed rows, or a host that lies, is not detectable by this gate).

**Mandatory host telemetry** (each a distinct source, reported with its failure reason `UNAVAILABLE` / `PERMISSION_DENIED` / `UNSUPPORTED` / `MALFORMED`): process names, process command lines, environment (a str→str mapping; an empty one is legitimately verified), home directory (taken from the **password database** for the effective UID, never from `$HOME`; it must be an existing, canonical, non-symlink directory owned by that user), `ifconfig -a` cross-checked against `ifconfig -l`, IPv4 and IPv6 routing tables, the `netstat -an` socket table, and the per-boot UUID; every external tool is run by **absolute system path** (never `PATH`), in a clean environment, only if it is a root-owned, non-group/other-writable regular file in root-owned directories; plus `/Volumes` and `diskutil list -plist` when any deny volume/UUID is named (both strictly validated; a malformed or implausibly empty value is `FAIL_CLOSED`). A verified-empty command-line list is impossible on a live system, so an empty or `launchd`-less one is treated as unavailable. **Mandatory configuration:** interlock state dir, the role's own state dir, role code root, a code manifest **and its SHA-256 pinned out-of-band**, and at least one deny-listed path/volume/UUID. Deny configuration is validated: paths absolute canonical (a leading `~/` is expanded against the trusted home; relative or `..` paths are refused), UUIDs well-formed, non-empty and non-duplicated, labels non-empty with no control/format characters or confusable-script letters. Label-only matching is reported `LABEL_ONLY` (weaker, advisory); prefer a UUID. A well-formed but wrong UUID matches nothing and cannot be detected.

**Plausibility floors (what they prove).** `ifconfig -a` lists at least two interfaces including a loopback carrying a 127/8 address and exactly the names `ifconfig -l` reports; each route table has its own address-family section, the exact column header and at least one loopback-interface row; the socket output is newline-terminated printable ASCII, begins and is sectioned by `Active …` headers, every examined section is followed by another section, and no data row may follow a blank line (a table running to the end of the output is treated as truncated; a multipath section with rows is refused). They show that the output was not obviously truncated or cut inside those structures. They do **not** prove that no row was removed from within a well-formed table, and exit status 0 is never treated as completeness.

**Checks:** per-boot identifier (`kern.bootsessionuuid`); advisory interlock; container runtime / control plane (process tokens, sockets, install directories, environment variables, optional process allowlist) — **not exhaustive**; network (interfaces: any non-loopback address or active status, loopback recognized **by address**, never by name; default routes in both families; sockets: TCP listeners/connections and UDP bound or connected beyond loopback; wildcard-only UDP/ICMP binds such as mDNS are inert without an addressed interface or route and are not counted); cloud-sync and agent **process** absence and, separately, **residual-exposure** absence; role workspace not under synchronized or Desktop/Documents paths; other role's storage absent; **code root equals a hash-pinned manifest**; weak owner-key / other-role-material scan of the role's own state.

**What the code allowlist proves and does not prove.** The role code root must equal the manifest exactly: every file's SHA-256 and size match, no unknown file or directory, no symlink, hardlink or special file, no group/other-writable or setuid file, wrong-owner files rejected, and no unlisted bytecode (none is allowed; run with `PYTHONDONTWRITEBYTECODE=1`). Every manifest path must also lie within a fixed role policy, so a manifest cannot add Qualification code. This proves the files under that root are byte-identical to that manifest. It does **not** prove the manifest is the reviewed one (that depends on the pin having been transcribed from a reviewed source), does not cover anything outside the root, and is not cryptographic provenance. **Path names alone are never treated as proof of Qualification absence.**

**Tree traversal.** The code root and role state are read descriptor-relative: the root and every directory are opened `O_DIRECTORY|O_NOFOLLOW` relative to their parent's open descriptor and must be the very device/inode the listing reported; members are opened relative to the open directory descriptor and must match the listed device/inode, size and mtime. A directory or file swapped after it was listed is detected and fails closed. Residual: ancestors of the root are resolved normally and hashing is point-in-time; a same-authority attacker who replaces both the manifest and its pin passes.

**What it cannot do:** it is not continuous (a process can pass and later re-enable networking, start a runtime, or launch a sync/agent process — the owner procedure must keep the whole phase clean); it is bypassable by a malicious owner/root or anyone who can alter the machine, the gate, its inputs or the manifest and its pin; it is a point-in-time check by software on the machine it guards; the socket table shows only sockets that exist at that instant and **UDP absence is not claimed**; the owner-key scan is name plus first-256-byte header evidence only (a renamed, encoded or late-header key is not detected); known-name and known-location lists are not exhaustive; it sees only the invoking user's home. Run as a read-only diagnostic on this host it fails (section 4).

### Interlock design (reboot-boundary log) — decision: option B for the claim, local advisory log retained
- **Decision:** cold-boot separation and physical detachment are owner-controlled physical procedures. The software log is an **operator-safety interlock, not a security isolation boundary**; it is **not** counted as a security boundary and **earns NO acceptance credit** (checks 11 and 13 and invariants 1 and 13 are `NOT_YET_PROVEN`).
- **Where state lives:** inside the *currently booted environment's own* interlock directory (created by an explicit `init`, mode 0700, owned by the current user). It is never shared between environments, so it creates no cross-role channel; a Witness environment does **not** see Forge's log, by design.
- **What it contains:** non-secret — role, per-boot UUID, sequence number, hash-chain link, environment id, checksum; plus `HEAD.json`. The directory must contain exactly `INIT.json`, `HEAD.json` and `receipts.jsonl`; any other entry (including a stale or planted temporary file) refuses the phase.
- **Hardening:** files are read through a no-follow, non-blocking open with the open descriptor checked (regular, single link, owned by the current user, not group/other-writable); the temporary `HEAD` file is created exclusively, without following symlinks, with a random name; carriage returns are rejected as non-canonical.
- **Concurrency and crash behaviour:** appends are serialized with an exclusive `flock()` on the interlock directory (verification takes a shared lock; no extra file is created). A writer that cannot obtain the lock, or whose platform does not support it, fails closed. The kernel drops the lock with the process, so there is no stale lock. If a writer dies between the receipt append and the HEAD replace, receipts and HEAD disagree and every later verification fails closed until the owner creates a new interlock directory. The lock coordinates cooperating writers only.
- **Who can write/delete it:** the OS user running the gate (and root). Anyone with that access can forge it by rewriting a consistent chain, replaying an older consistent `(receipts, HEAD)` pair, or deleting and re-`init`-ing (all tested or documented).
- **If unavailable/unverifiable:** `FAIL_CLOSED`.
- **What it resists:** accidental mixing of roles inside **one booted OS** and accidental corruption. **What it does not resist:** any deliberate writer, root, malicious owner, or firmware/boot-chain compromise. **Why keep it:** it costs little and turns a silent same-OS mistake into a refusal; it adds nothing against an adversary and is not relied upon.
