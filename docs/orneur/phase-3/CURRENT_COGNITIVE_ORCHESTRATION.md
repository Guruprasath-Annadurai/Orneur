# Current Cognitive Orchestration — Pre-Phase-3 Audit

Read before any Phase 3 code was written. Maps every place a request-shaping *cognitive* decision (as opposed to infrastructure/auth decisions) is currently made, where, and how.

## Decision inventory

| Decision | Where | Mechanism | Notes |
|---|---|---|---|
| Which model tier serves this request | `orca/serve/registry.py::resolve_tier_backend/resolve_tier_model` | **Hard-coded + rules-based** | Static per-tier config (`CONFIG.ollama.model_*`) with a step-down fallback chain (`ultra→core→nano`) if a configured model isn't installed. Not touched by Phase 2/2.1; stays authoritative for deployment eligibility. |
| Whether to escalate a self-hosted tier to a frontier backend for THIS query | `orca/serve/routing.py::decide_route` | **Rules-based (regex heuristics)** | `classify_query()` pattern-matches for time-sensitive language (`_TIME_SENSITIVE_PATTERNS`) and complex-reasoning language (`_COMPLEX_REASONING_PATTERNS`), plus a raw word-count threshold. This is Orca's only existing **freshness-adjacent** and **complexity-adjacent** signal today — explicitly documented in its own module as "a heuristic, not a certainty." Gated by 4 independent conditions (opt-in flag, sovereignty lock, credentials present, daily cap). |
| Whether to use tools, and which | `orca/brain/agent.py::AgentLoop._plan` | **Model-generated** | A dedicated LLM call (`PLANNER_SYSTEM`) asks the brain itself to output `{"action": "direct"}` or `{"action": "tools", "calls": [...]}`. Not deterministic — the same input can plan differently across calls. This is the ONLY tool-triggering mechanism; there is no rules-based override or fallback if the model's JSON is malformed (falls back to `{"action": "direct"}` on parse failure, silently skipping tools rather than erroring). |
| Whether to reflect/self-critique before returning | `orca/brain/agent.py::AgentLoop.run/stream` | **Rules-based (deterministic)** | `word_count(draft) > REFLECTION_THRESHOLD (150)`. Simple, explicit, documented threshold. |
| Whether to recall short-term/long-term memory | `orca/serve/api.py` (`/api/chat` line ~598, `/api/stream` line ~764) | **Hard-coded, always-on** | `sess.memory.recall_context(req.message, n=3)` runs unconditionally on every single chat/stream request — there is no "does this request need memory" decision at all today. This is the clearest gap Phase 3's `requires_memory` field is meant to make explicit and eventually conditional. |
| Whether to retrieve from uploaded documents (RAG) | `orca/serve/api.py::/api/stream` (line ~771) | **Implicit, session-state-driven** | `if sess.doc_store.count() > 0:` — RAG triggers purely because the session happens to have uploaded documents, regardless of whether the current message actually needs them. No per-message "does this need retrieval" classification exists. `/api/chat` (non-streaming) does not appear to check `doc_store` at all — an inconsistency between the two endpoints worth flagging, not fixing in Phase 3. |
| Whether knowledge-graph extraction runs | `orca/serve/api.py::/api/stream` (line ~839) | **Hard-coded, always-on (background)** | Fire-and-forget background task after every response; not conditional on intent. |
| Ultra (multi-agent) mode | `orca/serve/api.py::/api/ultra` → `orca/variants/ultra.py::OrcaUltra` | **Model-generated decomposition, user-selected entry point** | The user/client explicitly calls `/api/ultra` (there's no automatic "this looks complex enough for Ultra" escalation from the normal chat path) — but ONCE inside Ultra, `DECOMPOSE_SYSTEM`'s LLM call decides subtask count/parallelism, and `GRADE_SYSTEM`'s LLM call decides whether to retry. Both fully model-generated, not rules-based. |
| Agent mode (tool-use loop itself) | `orca/brain/agent.py::AgentLoop` | **Always active** | Every `/api/chat`/`/api/stream` request already runs through the full THINK→PLAN→ACT→RESPOND→REFLECT pipeline — there is no "conversational, no agent needed" fast path today. Every request pays for at least one planning LLM call even when the answer is a simple greeting. |
| Fallback when a tier's model isn't installed | `orca/serve/registry.py` | **Rules-based (deterministic step-down)** | `ultra → core → nano`, logged via `on_fallback`. Unrelated to cognitive intent — purely an availability fallback. Already identified in Phase 2.1 as the reason Aeternum's `MODEL_NOT_ROUTABLE` path isn't observable through live `/api/chat` (this chain resolves away from "ultra" before the Gateway ever sees the request). |
| Model tier access (free/pro/enterprise gating) | `orca/auth/store.py::model_access_allowed` | **Rules-based, authorization** | Not a cognitive decision at all — this is entitlement/authorization, explicitly out of scope for Phase 3's risk/intent work per the phase spec ("risk classification is NOT authorization"). |
| Input moderation action (block/support/flag) | `orca/serve/moderation.py::check_input` | **Rules-based (pattern matching)** | Runs before any cognitive decision; orthogonal to intent/complexity/risk as designed in Phase 3 (moderation decides content policy, not task shape). |
| Image/video vs. text generation intent | `orca/lens/intent.py::detect_generation_intent` | **Rules-based (regex/keyword)** | A narrow, PRE-EXISTING, orthogonal intent detector — classifies image/video/chat BEFORE a request reaches any text tier, short-circuiting generation requests away from Genesis/Novus/Aeternum entirely. Explicitly documented as "not a trained classifier" with known false-negative/positive tradeoffs, the same honesty standard as `routing.py`. Unrelated to and not superseded by Phase 3's `IntentCategory` taxonomy (that classifies TEXT task shape — FACTUAL/CODING/etc. — this classifies generation MEDIUM). Both are real, both stay. |
| Frontier vs. self-hosted execution path | `orca/serve/api.py` (`backend_resolution.backend != "ollama"`) | **Rules-based, derived from tier config + routing decision** | A structurally different code path (`_generate_via_frontier_backend`, single-turn, no tools) vs. the full `_Session`/`AgentLoop` path. This branch point is a real, pre-existing "capability availability" decision Phase 3's operation support-states (`SUPPORTED_NOW`/`UNAVAILABLE`) should describe honestly rather than duplicate. |

## Duplicated / implicit logic worth naming explicitly

- **Complexity and freshness signals already exist, but only inside `routing.py`, only for the cost-escalation decision, and only as a byproduct.** `QueryComplexity` (is_time_sensitive, is_complex, word_count) is real, tested, rules-based logic Phase 3's `ComplexityAssessment`/`FreshnessRequirement` classifiers should be able to reuse or wrap, not reinvent from scratch — but its current name and shape are scoped narrowly to "should we escalate to a paid backend," not general-purpose cognition. Phase 3 must decide whether to promote it to a shared primitive or keep it routing-specific and build parallel (documented explicitly either way in `COGNITIVE_CONTRACTS.md`/`INTENT_COMPILER.md`).
- **Tool-use planning is 100% model-generated with no rules-based floor.** There is no deterministic classification of "this obviously needs `web_search`" independent of asking the LLM. Phase 3's Intent Compiler is explicitly required to be "deterministic/rules-first" — this is a real gap it's meant to start closing, not something to leave duplicated.
- **Memory recall has no gating at all** — always on, every request. This is the single clearest "implicit" decision in the whole system: nothing currently asks "does this request need memory," it's simply always fetched. Phase 3's `IntentPlan.requires_memory` field should describe this honestly as `SUPPORTED_NOW` and, for Phase 3, is allowed to just always evaluate to `True` for the existing self-hosted path (see `CUTOVER.md`) — the point is naming the decision, not necessarily changing its answer yet.
- **RAG triggering is state-driven (doc count), not intent-driven**, and inconsistent between `/api/chat` and `/api/stream`. Phase 3 should represent `requires_retrieval` as a real field the Kernel computes, and route it to the existing `doc_store.count() > 0` check as the `SUPPORTED_NOW` execution policy for Phase 3 — again, not a redesign of RAG, just an honest label on existing behavior.
- **No existing concept of budget, risk, or evidence requirement anywhere in the current orchestration.** These are wholly new to Phase 3 — there's nothing to migrate or preserve for these three; they should be built as pure additions that don't yet change any currently-firing decision (see `EXECUTION POLICY` in `ARCHITECTURE.md`).

## What Phase 3 must NOT delete or break

- `orca/serve/routing.py`'s cost-aware escalation mechanism (4-gate opt-in design, daily cap, sovereignty lock) — real, tested, load-bearing product behavior. Phase 3 moves/wraps its decision behind the Cognitive Kernel/model-policy boundary per the phase spec's §29, but the underlying gates and logic stay exactly as they are.
- `AgentLoop`'s THINK→PLAN→ACT→RESPOND→REFLECT pipeline — Phase 3 makes the Kernel *authoritative for planning what happens before* this pipeline runs (model policy, budget, operation support states), not a replacement for it. The existing self-hosted Ollama path (`_Session`/`AgentLoop`/tools/memory/RAG) remains the `SUPPORTED_NOW` execution target for Phase 3's `ANSWER_DIRECTLY`/`REASON`/`USE_TOOL`/`RECALL_MEMORY` operations.
- The Phase 2.1 Gateway cutover itself — the Kernel calls `ModelGateway` exactly the way `orca/serve/api.py` does today (via `brain_for_tier_resolution`/`GatewayBrain`), never a raw runtime.
