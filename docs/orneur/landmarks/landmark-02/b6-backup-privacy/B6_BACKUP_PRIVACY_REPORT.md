## 2. What was built
**Format `orneur-backup/2`** (`orca/serve/backup.py`, `backup_crypto.py`): one file; AES-256-GCM (library `cryptography`) in 1 MiB frames, per-archive key derived with HKDF-SHA256 from the operator's key and a random salt; every frame's AAD binds the header, the frame counter and a final-frame flag, so reordering, dropping, duplicating, truncating (even at a frame boundary), appending and bit flips all fail authentication. The manifest is *inside* the encrypted stream, so it cannot be rewritten by someone who can only write the archive. The archive appears under its final name only once complete and fsynced (`.partial` + `os.replace`); the transient per-database snapshot lives in a private 0700 scratch directory removed afterwards.

**Key custody** is the operator's: `load_key` reads a base64 32-byte key from `--key-file`/`ORNEUR_BACKUP_KEY_FILE`; it **never generates one implicitly**, refuses a missing file, a file readable by group/other, a wrong length, and a path inside the data directory or the backup destination. `orca data-backup keygen <path>` is an explicit one-off helper (refuses to overwrite, mode 600) — using it, or any other source, is the founder's custody decision. Wrong key, tampering and truncation are deliberately indistinguishable (`BackupAuthError`).

**Deletion-aware restore.** A new append-only **deletion ledger** (`orca/serve/deletion_ledger.py`, `deletion_ledger.jsonl` in the data directory, identifiers only) is written by the live deletion paths *before* the destructive work and fails closed (conversation tombstone, document removal, account deletion). It is **excluded from backups** and preserved by restore, so history is never stored only inside the backup it must override. `restore` needs an authoritative history from at least one of: the target's live ledger (+ its conversation tombstones), or an HMAC-authenticated **export** (`data-backup export-deletions`) generated *after* the backup (an older one is refused). With neither it **refuses** (`DeletionHistoryUnavailable`). An explicit `--unsafe-without-deletion-history` override exists for disaster recovery; it restores, reports `deleted_data_may_be_present: true`, and writes no ledger (an empty one would later pass for authoritative).
Applied to the staged copy before it goes live: deleted conversations get a tombstone (access revoked the moment the directory is served; the existing sweep finishes any remaining cascade on start) and their transcript rows are removed; deleted documents leave the registry and keyword fallback; deleted accounts are removed with the product's own `delete_account_rows`.

**All-or-nothing restore.** Decrypt into a private staging directory beside the target → verify every file's hash/size, SQLite `integrity_check`, required components, no unlisted/duplicate/unsafe paths → apply deletions → health-check (integrity, deleted conversations have no rows and a tombstone, deleted accounts absent) → swap. A fresh target is one `rename`. A populated target uses a **write-ahead journal** (`.restore-journal.json`): originals are moved to `.pre-restore-<id>/`, restored entries moved in, post-swap health check, and *any* failure — exception or `KeyboardInterrupt` — rolls everything back to the exact previous bytes (tested at every swap step). If the process itself dies, the journal remains: `/readyz` reports not-ready (`restore.status: interrupted`), a new restore is refused, and `orca data-backup recover` (idempotent) restores the previous state. Things outside the backup's scope (`vault/`, models, cache, a live file the backup never had) are not replaced.

**Consistency.** SQLite databases are online-backup snapshots (consistent with a writer active — tested). Any other file that changes while being copied is retried, then listed as `unstable`; the backup is flagged `consistent: false` and `restore` refuses it unless `--allow-inconsistent`. `verify` is a full decrypt-and-check (not just a hash comparison).

## 3. Defects found while building (all fixed, tested)
* **Freed pages**: the first live run (real server + CLI) showed the deleted conversation's text still inside `turns.db` after restore — deleted rows left their bytes in free pages. Staged databases now run with `secure_delete=ON` and are `VACUUM`ed after deletions; asserted on raw file bytes for conversations and account emails.
* Write-ahead gap: the first swap journal recorded a move *after* doing it, so a crash between the two could not be undone. The journal entry is now written first; recovery tolerates a move that never happened.
* A leftover `.restore-journal.json.tmp` after a crash while writing the journal itself.
* The post-swap health check scanned the rollback directory.

## 5. Incompatible change
The earlier plaintext directory format (`MANIFEST.json` + files) can no longer be created or restored, and `orca data-backup create` now takes an archive path plus a key instead of a directory. Existing plaintext backups must be restored by hand or replaced by a new encrypted backup. `orca backup --keep N` (auth DB) is unchanged.

## 6. What is NOT solved — limitations and BLOCKED items
* **BLOCKED — founder decision: key custody.** Where the key lives, who holds copies, rotation and escrow. The code enforces separation from the data and the archive; it cannot choose a custody model. Losing the key makes every backup unrecoverable (by design; there is no recovery path).
* **BLOCKED — founder decision: retention of historical backups and immutable/off-host storage.** A deletion changes live data and the ledger; it does **not** change an archive that already exists. Older backups remain recoverable by anyone holding the key until the operator destroys them. No irreversible erasure of offline copies is claimed or possible here; the deletion response now says so.
* **Deletion history after the last export.** Restoring onto a *new* machine can only honour deletions up to the export's time; deletions between the last export and a total loss of the old machine are unknowable. Take exports regularly and keep them off-host; otherwise the override (and its warning) is the only path.
* **Opaque identifiers are retained** in the ledger (session/document/account ids and the owner id, no content, no email) so a restore can honour them; they persist after the data is deleted.
* Vector-store (Chroma) segment files are copied as files: consistent only when the server is stopped (the flag detects writes *during* the copy, not a store that is inconsistent with the databases at one instant). Chunks of a document deleted after the backup remain in the restored vector store but are unreachable (registry-enforced retrieval) until the reconciler removes them. Per-conversation memory stores of a deleted conversation are removed by the existing deletion sweep after start, not during restore.
* Restore needs the server stopped; this is not enforced. The `.pre-restore-*` rollback copy holds the previous contents in plaintext until the operator deletes it.
* Backup creation briefly writes one database snapshot in plaintext to a private scratch directory beside the archive; it is removed, not securely wiped from the device.
* Not tested: very large data directories, off-host transport, a real KMS/HSM, restore on a different SQLite version, a concurrent restore and a running server.
