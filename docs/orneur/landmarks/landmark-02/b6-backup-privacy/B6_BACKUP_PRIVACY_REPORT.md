## 2. What was built
**Format `orneur-backup/2`** (`orca/serve/backup.py`, `backup_crypto.py`): one file; AES-256-GCM (library `cryptography`) in 1 MiB frames, per-archive key derived with HKDF-SHA256 from the operator's key and a random salt; every frame's AAD binds the header, the frame counter and a final-frame flag, so reordering, dropping, duplicating, truncating (even at a frame boundary), appending and bit flips all fail authentication. The manifest is *inside* the encrypted stream, so it cannot be rewritten by someone who can only write the archive. The archive appears under its final name only once complete and fsynced (`.partial` + `os.replace`); the transient per-database snapshot lives in a private 0700 scratch directory removed afterwards.

**Key custody** is the operator's: `load_key` reads a base64 32-byte key from `--key-file`/`ORNEUR_BACKUP_KEY_FILE`; it **never generates one implicitly**, refuses a missing file, a file readable by group/other, a wrong length, and a path inside the data directory or the backup destination. `orca data-backup keygen <path>` is an explicit one-off helper (refuses to overwrite, mode 600) — using it, or any other source, is the founder's custody decision. Wrong key, tampering and truncation are deliberately indistinguishable (`BackupAuthError`).

**Deletion-aware restore.** (Corrected in §7: the ledger is hash-chained but still an editable file.) A new append-only **deletion ledger** (`orca/serve/deletion_ledger.py`, `deletion_ledger.jsonl` in the data directory, identifiers only) is written by the live deletion paths *before* the destructive work and fails closed (conversation tombstone, document removal, account deletion). It is **excluded from backups** and preserved by restore, so history is never stored only inside the backup it must override. `restore` needs an authoritative history from at least one of: the target's live ledger (+ its conversation tombstones), or an HMAC-authenticated **export** (`data-backup export-deletions`) generated *after* the backup (an older one is refused). With neither it **refuses** (`DeletionHistoryUnavailable`). An explicit `--unsafe-without-deletion-history` override exists for disaster recovery; it restores, reports `deleted_data_may_be_present: true`, and writes no ledger (an empty one would later pass for authoritative).
Applied to the staged copy before it goes live: deleted conversations get a tombstone (access revoked the moment the directory is served; the existing sweep finishes any remaining cascade on start) and their transcript rows are removed; deleted documents leave the registry and keyword fallback; deleted accounts are removed with the product's own `delete_account_rows`.

**All-or-nothing restore.** Decrypt into a private staging directory beside the target → verify every file's hash/size, SQLite `integrity_check`, required components, no unlisted/duplicate/unsafe paths → apply deletions → health-check (integrity, deleted conversations have no rows and a tombstone, deleted accounts absent) → swap. A fresh target is one `rename`. A populated target uses a **write-ahead journal** (`.restore-journal.json`): originals are moved to `.pre-restore-<id>/`, restored entries moved in, post-swap health check, and *any* failure — exception or `KeyboardInterrupt` — rolls everything back to the exact previous bytes (tested at every swap step). If the process itself dies, the journal remains: `/readyz` reports not-ready (`restore.status: interrupted`), a new restore is refused, and `orca data-backup recover` (idempotent) restores the previous state. Things outside the backup's scope (`vault/`, models, cache, a live file the backup never had) are not replaced.

**Consistency.** SQLite databases are online-backup snapshots (consistent with a writer active — tested). Any other file that changes while being copied is retried, then listed as `unstable`; the backup is flagged `consistent: false` and `restore` refuses it unless `--allow-inconsistent`. `verify` is a full decrypt-and-check (not just a hash comparison).

## 3. Defects found while building (all fixed, tested)
* **Freed pages**: the first live run (real server + CLI) showed the deleted conversation's text still inside `turns.db` after restore — deleted rows left their bytes in free pages. Staged databases now run with `secure_delete=ON` and are `VACUUM`ed after deletions; asserted on raw file bytes for conversations and account emails.
* Write-ahead gap: the first swap journal recorded a move *after* doing it, so a crash between the two could not be undone. The journal entry is now written first; recovery tolerates a move that never happened.
* A leftover `.restore-journal.json.tmp` after a crash while writing the journal itself.
* The post-swap health check scanned the rollback directory.

## 5. Incompatible change
The earlier plaintext directory format (`MANIFEST.json` + files) can no longer be created or restored, and `orca data-backup create` now takes an archive path plus a key instead of a directory. **CORRECTED:** the claim that `orca backup --keep N` was left unchanged was the bypass itself — it is now retired (§7).

## 6. What is NOT solved — limitations and BLOCKED items
* **BLOCKED — founder decision: key custody.** Where the key lives, who holds copies, rotation and escrow. The code enforces separation from the data and the archive; it cannot choose a custody model. Losing the key makes every backup unrecoverable (by design; there is no recovery path).
* **BLOCKED — founder decision: retention of historical backups and immutable/off-host storage.** A deletion changes live data and the ledger; it does **not** change an archive that already exists. Older backups remain recoverable by anyone holding the key until the operator destroys them. No irreversible erasure of offline copies is claimed or possible here; the deletion response now says so.
* **Deletion history after the last export.** Restoring onto a *new* machine can only honour deletions up to the export's time; deletions between the last export and a total loss of the old machine are unknowable. Take exports regularly and keep them off-host; otherwise the override (and its warning) is the only path.
* **Opaque identifiers are retained** in the ledger (session/document/account ids and the owner id, no content, no email) so a restore can honour them; they persist after the data is deleted.
* Vector-store (Chroma) segment files are copied as files: consistent only when the server is stopped (the flag detects writes *during* the copy, not a store that is inconsistent with the databases at one instant). Chunks of a document deleted after the backup remain in the restored vector store but are unreachable (registry-enforced retrieval) until the reconciler removes them. Per-conversation memory stores of a deleted conversation are removed by the existing deletion sweep after start, not during restore.
* Restore needs the server stopped; this is not enforced. The `.pre-restore-*` rollback copy holds the previous contents in plaintext until the operator deletes it.
* Backup creation briefly writes one database snapshot in plaintext to a private scratch directory beside the archive; it is removed, not securely wiped from the device.
* Not tested: very large data directories, off-host transport, a real KMS/HSM, restore on a different SQLite version, a concurrent restore and a running server.

## 7. Corrective pass — legacy bypass and ledger challenge (CTO finding, P1)
**Finding.** `orca/ops/backup.py` (`backup_sqlite`, `backup_postgres`, `run_backup`, `restore_sqlite`) and the CLI commands `orca backup` / `orca restore` were left working. Reproduced on the candidate (`evidence/b6c_legacy_bypass_red_b1c56b9.txt`, 4 of 4): a plaintext copy of the accounts database containing a synthetic customer email was written, and a legacy restore brought an account deleted after the backup back. (A second, smaller plaintext copy — the one-time `auth.db.pre-migration-*.bak` — is documented in `B6_LEGACY_MIGRATION.md`; it is not a backup tool and was not changed.)

**Fixed (fail-closed, no second restore route).**
* `backup_sqlite`, `backup_postgres`, `run_backup`, `restore_sqlite` raise `BackupError` pointing to `orca data-backup`; `orca backup` and `orca restore` exit 1 with the same pointer (`--keep`/`--no-prune`/`--yes` still parse so an old cron line fails with an explanation instead of silently doing something else). `orca backups` still lists existing plaintext files, with a warning; `prune_old_backups` still removes them. No programmatic path writes or restores plaintext any more.
* **Offline migration** of existing plaintext SQLite backups: `orca data-backup import-legacy` — source and output must be outside the live directory, refused while a server runs, source opened read-only and integrity-checked, never touches the live directory, never deletes the original, restores only through the normal protected `restore` (`B6_LEGACY_MIGRATION.md`). Postgres dumps: manual/BLOCKED.

**The ledger, challenged.** Before: any file (missing, empty, truncated, edited, extended with a forged line) was either trusted or silently re-created as an "authoritative" empty history. Now: each line commits to the previous one behind a random per-ledger genesis id; the backup manifest (inside the authenticated archive) records the ledger id, length and head; an authenticated export records the same.
| Attack | Result now (`tests/test_l02_b6_corrective.py`) |
|---|---|
| ledger removed, then another backup taken (fresh empty ledger) | restore of the older backup **refused** (lineage mismatch) |
| truncated to empty / garbage / unchained lines | **refused** (no genesis / chain broken) |
| forged unchained line (e.g. to make a restore delete someone's conversation) | **refused**; nothing applied |
| middle entry edited / removed / reordered | chain broken → **refused** |
| live ledger cut back to a valid prefix while an export knows more | **refused** ("behind the export") |
| export from another ledger lineage; export older than the backup; edited or wrongly keyed export | **refused** |
| **consistent rewrite of the whole chain by someone with write access; entries removed after the last copy kept elsewhere; a forged but correctly chained entry** | **NOT detectable locally.** The restore result says so: `completeness_verified: false`, `live_ledger_authenticated: false`, `off_host_anchor: false` and a plain-language statement |
A damaged ledger never blocks a customer's deletion: the damaged file is set aside and a new lineage starts (a later restore will not treat it as a continuation of older backups).
**Not tamper-proof; not independently authoritative.** Verifying completeness needs an append-only anchor outside this host (WORM storage, a second host, a signed external log) — a founder-controlled custody and infrastructure decision, **BLOCKED**, not simulated here. A working local restore and verified deletion-history completeness are different things; this tool provides the first and states plainly that it does not provide the second.

**Reviewed and changed.**
* *Recovery journal*: it drives deletions and moves, so it is now validated before use (regular file owned by this user and not group/world-writable; holding directory name `.pre-restore-<10 hex>`; entry names are single safe path components; lists of strings). Path escapes (`../x`, absolute paths, nested names, wrong types, non-JSON) are refused with the directory left flagged and nothing touched; a symlink in place of a restored entry is unlinked, never followed.
* *Permissions*: restored directories are 0700 and files 0600 (before, they inherited the umask). A deployment that relied on group access must re-grant it deliberately. Files the backup never contained keep their modes.
* *Concurrent restore*: an exclusive lock per target; a second restore fails with "another restore is in progress".
* *Running server*: every server process holds a shared lock on `<data dir>/.server.lock` for its life (taken in the application lifespan); a restore needs the exclusive lock, so it **refuses while any server is up**, and a server **refuses to start while a restore holds the directory**. If the process dies mid-swap the journal makes `/readyz` report not-ready and blocks further restores until `data-backup recover`. Advisory `flock` on a local filesystem — not reliable across NFS; a process that was already running without the lock (an older version) is not detected.
